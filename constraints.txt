# Exact versions of every Python distribution noctornal-api and
# noctornal-ontology install, with their dev extras and db/requirements.txt.
#
# Why this exists (sec-pin-dependencies, 2026-09-23). Every dependency in
# apps/api/pyproject.toml is a floor (`fastapi>=0.110`), which is right for
# a package and wrong for a release: a clean install resolves each floor to
# whatever is newest on the day, so the clean VM of the Alpha 6 pre-release
# check ran starlette 1.7.0, uvicorn 0.53.0, alembic 1.20.0, psycopg 3.3.6
# and SQLAlchemy 2.0.54 while the suite had passed on the versions below
# (release/CLEAN-VM-INSTALL.md, F17 and G9). A test run proves the stack it
# ran on, and nothing else.
#
# A CONSTRAINTS file, not a requirements file: it pins a version only when
# something already asks for the distribution, and never adds one. So the
# dependency SET stays declared in one place, the pyproject files, and this
# file only decides which release of each. The installers, the Dockerfile and
# CI all install with `-c constraints.txt`, and
# apps/api/tests/test_dependency_pins.py holds all of them to it, holds every
# declared dependency to a pin inside its declared range, and holds the pins
# to the environment the suite is running in.
#
# These are the versions in the development environment the Alpha 6 suite
# passed on. Every one of them publishes wheels for CPython 3.12, 3.13 and
# 3.14 on Linux (x86_64 and aarch64), Windows and macOS, checked against PyPI
# when this was written, so the installers' "3.12 or newer" still installs
# without a compiler.
#
# To move a pin: change it here, reinstall with
#     python -m pip install -c constraints.txt -e packages/ontology -e "apps/api[dev]"
# run the suite, and commit the two together. A distribution a new
# dependency brings in must be added here, or test_dependency_pins fails.
#
# Not pinned here: pip itself (the installers upgrade it first), and the
# build backend an editable install fetches into its own isolated build.
